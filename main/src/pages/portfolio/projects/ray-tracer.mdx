During my master's year I learnt about different rendering paradigms and techniques. 
I was smitten by ray tracing's simple concept and the rendering equation, so building a ray tracer and implementing some of the many techniques I read about has been a goal of mine ever since. 

This application stems from a piece of coursework for my rendering module which, although enough for an honorable mark, was inaccurate, clunky, and slow - the holy trinity. 

This project has been and still is a great way for me to deepen my knowledge of computer graphics, 3D maths and C++ programming.

<Ellipsis />

A quick win, and my first task was to refactor the 3D maths used in the application, the data structures and routines, to be faster and more accurate. These include vectors, quaternions and matrices. I started with common optimisations such as loop-unravelling and using bitwise operations or unsigned integer arithmetic to minimise CPU cycles. <Link to="https://www.agner.org/optimize/#manuals">Agner Fog's C++ optimisation guides </Link> are a treasure trove of information for explaining these tricks.

I also researched _SIMD parallelism_ and vectorised some of my maths data structures using the built-in intrinsics in `xmmintrin.h`. This reduces the number of operations needed resulting in better CPU usage and a pretty dramatic decrease in run-time for the same un-vectorised operation (in my case a 200% speed-up for tasks such as matrix multiplication or vector addition).


<Figure caption="C++ code for matrix transpose with intrinsics.">
    ```cpp
    // transpose a 4x4 matrix
    Matrix4 Matrix4::transpose(const Matrix4& mat) 
    {
        __m128 c0c1 = _mm_shuffle_ps(mat.__m[0], 
            mat.__m[1], _MM_SHUFFLE(1, 0, 1, 0));
        __m128 c2c3 = _mm_shuffle_ps(mat.__m[2], 
            mat.__m[3], _MM_SHUFFLE(1, 0, 1, 0));
        __m128 c1c0 = _mm_shuffle_ps(mat.__m[1], 
            mat.__m[0], _MM_SHUFFLE(2, 3, 2, 3));
        __m128 c3c2 = _mm_shuffle_ps(mat.__m[3], 
            mat.__m[2], _MM_SHUFFLE(2, 3, 2, 3));
        Matrix4 t;
        t.__m[0] = _mm_shuffle_ps(c0c1, c2c3, 
            _MM_SHUFFLE(2, 0, 2, 0));
        t.__m[1] = _mm_shuffle_ps(c0c1, c2c3, 
            _MM_SHUFFLE(3, 1, 3, 1));
        t.__m[2] = _mm_shuffle_ps(c1c0, c3c2, 
            _MM_SHUFFLE(1, 3, 1, 3));
        t.__m[3] = _mm_shuffle_ps(c1c0, c3c2, 
            _MM_SHUFFLE(0, 2, 0, 2));
        return t;
    }
    ```

As my application grew in size and complexity, I quickly found myself hindered by the limitations of my development environment. My original coursework used **OpenGL 1.1** (which can be carbon dated to the Jurassic era) and, due to its much smaller scope and lack of external dependencies bar the **Qt** GUI library, was manageable on the small Linux partition on my laptop without an IDE. 

Once I could raytrace objects, I migrated the project to a Windows environment to use Visual Studio and modern **OpenGL 4.5** features.

To manage the third party libraries I would now need, I learnt to use **CMake** and wrote a script to generate Visual Studio solutions. Adding external code is now only requires editing a CMakeList file and running the script, no arcane Visual Studio knowledge needed!

I used this change as an occasion to make deep modifications to the application's architecture, such as using **Dear ImGui** instead of **Qt** for the GUI. So much so that practically nothing of the original coursework remains.

As a scene's complexity increases, so does the need for acceleration techniques, unless one has the patience of a saint or just likes wasting their time.
In this application, I have added two very common acceleration methods.

The first is an implementation of a Bounding Volume Hierarchy (BVH). I implemented a simple mid-point axis BVH, which builds a tree by recursively splitting the scene into two nodes. The split is along the axis of the mid-point of the geometric primitives within the node. I then implemented a linear BVH (LBVH), which is a bit more sophisticated but results in a faster and more reliable performance.

<Figure caption="From top: mid-point BVH, LBVH"> 
    <img src="/assets/midPointBVH.png" alt="mid-point bounding volume hierarchy"/>
    <img src="/assets/horizontalBVH.png" alt="linear bounding volume hierarchy"/>
</Figure>

A LBVH is particulary useful for GPUs as building them is easily parallelisable. They are based on mapping "treelets", small subtrees of scene primitives that are close together, to <a href="https://en.wikipedia.org/wiki/Z-order_curve">Morton code</a> primitives (a mapping of multidimensional data to a single dimention, like an array). 

Using these primitives, the treelets are sorted using the <a href='https://en.wikipedia.org/wiki/Radix_sort'>radix sort algorithm</a> such that nearby treelets are in contiguous segments. We could use other sorting algorithms, but for a large number of treelets radix sort is appropriate and GPU friendly as the algorithm doesn't branch and works well with vectorisation. 

Flattening the tree into a single compact array, with cache-aligned nodes, allows for much faster tree traversal.

The second is multithreading, harnessing the multiple cores in modern CPUs and dividing the rendering task which is thankfully embarassingly parallel. 

I implemented a thread pool using C++'s `std::thread` interface and a thread-safe, lock-based stack for processing tasks.

<Figure caption="C++ thread pool initialisation and worker function"> 
    ```cpp
    ThreadPool::ThreadPool(const size_t& threadCount)
        : threadCount{ threadCount ? 
        threadCount : std::thread::hardware_concurrency()},
        tasksCount{ 0 }, workers{}, running{ true }, tasks{}
    {
        workers.reserve(threadCount);
        for (size_t t = 0; t < threadCount; ++t)
        {
            workers.push_back(
                std::thread(&ThreadPool::worker, this));
        }
    }

    // worker threads are launched by invoking the `ThreadPool::worker()` method
    void ThreadPool::worker()
    {
        std::function<void()> task; 
        while (running)
        {
            // pop() moves the task from task stack to worker
            if (tasks.pop(task))
            {
                task();
                tasksCount--;
            }
        }
    }
    ```
</Figure>

Rendering in parallel with four cores provides a consistent 600% speedup compared to serial implementations.
However, because of the relatively small number of primitives in this scene the speedup provided by the LBVH, although still around 16%, is not consequential. An interesting feature of the data is the difference in standard deviation between the non-BVH and LBVH implementations which I believe is a feature of the more cache coherent BVH structure.\\
Whereas it seems to stabilise at around 1000 ms for the LBVH, it is much higher for the non-BVH and as large as 19775 ms for the serial implementation of 20 samples per pixel. That's almost a 20 second difference between the slowest and fastest measurement!

Ideally for a task taking time `T` to complete on `N` cores, the application will finish in `T / N` time. 

A naive approach to dividing the image pixels would be to divide it into `N` sections, irrespective of the scene's geometry, and assign each section to a thread.

This assumes that `T` is the same for each section, but not all pixels are born equal. Indeed, pixels for a ray with many bounces will take longer to compute than a ray with few bounces. 

As the overall rendering time of the image is bounded by the slowest thread, we are denied the ideal T / N runtime.

This calls for a smarter division of the image amongst threads.

To help determine a better task per thread allocation, I created some heatmaps (blue = min, red = max) showing the overall complexity for a scene.

Using this data, perhaps with a simple first pass, the time taken computing an ideal task allocation could be offset by the overall gain on the final image render time. 

Alternatively, one could turn each individual pixel into a task, that each worker from the pool can pick up.
